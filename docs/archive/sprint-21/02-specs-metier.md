# Spécifications Fonctionnelles : Lot 4 — Sprint 21 (Données Réelles Stats & Compatibilité MySQL/MariaDB)

## 1. Règles de Gestion (RG) et Cas Limites
| ID RG | ID US Liée | Description de la règle métier | Comportement en cas d'erreur / Cas limite |
|---|---|---|---|
| `RG-01` | `US-LOT4-05` | Le champ `gender` sur `members` est **strictement optionnel** (valeur par défaut `NULL` = « Non renseigné »). Valeurs autorisées : `NULL`/`""` (Non renseigné), `'M'` (Homme), `'F'` (Femme), `'O'` (Autre / Non binaire). | Toute valeur hors `{null, '', 'M', 'F', 'O'}` envoyée via API (`POST /api/v1/members`, `PUT/PATCH /api/v1/members/{id}`, `POST /api/v1/registrations`) est rejetée avec un code JSend `422` et un message explicite. |
| `RG-02` | `US-LOT4-05` | Dans le CRM (`/members`, création et édition) et dans le tunnel d'inscription (`/register`), un sélecteur optionnel « Genre (optionnel) » permet de renseigner la valeur. Pour le rôle **Entraîneur**, la fiche individuelle reste anonymisée (pas d'exposition des données privées sur `GET /api/v1/members`). | Si le champ n'est pas touché par l'utilisateur, la valeur `NULL` est persistée sans bloquer la validation du formulaire. |
| `RG-03` | `US-LOT4-06` | Les ratios démographiques calculés par `StatsService` et `SystemController::getKpis()` reflètent **100 % les données réelles** de `members.gender` dans le périmètre de l'utilisateur connecté (tous les adhérents pour le Bureau/Superadmin, uniquement les élèves de ses disciplines pour l'Entraîneur). Les valeurs retournées incluent `male`, `female`, `other`, `unspecified` et leurs pourcentages respectifs (`male_pct`, `female_pct`, `other_pct`, `unspecified_pct`). | Si l'effectif est `0`, tous les pourcentages valent `0`. Si aucun adhérent n'a renseigné son genre, `male_pct = 0`, `female_pct = 0`, `unspecified_pct = 100` (jamais `54 / 46`). |
| `RG-04` | `US-LOT4-06` | Sur `/stats`, la carte KPI « Répartition H / F » (`#kpi-gender-ratio`) affiche les pourcentages réels et le sous-libellé affiche la répartition réelle des fiches renseignées / non renseignées (ex. `X % non renseigné` ou `Données réelles`), en supprimant définitivement la mention « Répartition estimée ». | Les mises à jour dynamiques via `stats.ts` (`GET /api/v1/stats/kpis`) mettent à jour à la fois `#kpi-gender-ratio` et le sous-libellé `#kpi-gender-details` de manière cohérente avec le rendu serveur PHP. |
| `RG-05` | `US-LOT4-07` | Le moteur PDO `Database` et l'ensemble des requêtes SQL Core (migrations `001`–`005`, transactions, upserts, inspections de colonnes) sont compatibles **SQLite 3 WAL** et **MySQL 8 / MariaDB 10.6+** via des helpers dialectaux centralisés dans `Database.php`. | Aucune requête Core en dehors de `Database.php` ne doit exécuter en dur `BEGIN IMMEDIATE`, `PRAGMA table_info`, `INSERT OR IGNORE`, `INSERT OR REPLACE` ou `ON CONFLICT(...) DO UPDATE` non adapté au driver actif. |
| `RG-06` | `US-LOT4-08` | Un script CLI de diagnostic (`npm run db:check-mysql`) vérifie : (1) la traduction DDL complète vers MySQL (`InnoDB`, `utf8mb4`, `AUTO_INCREMENT`), (2) l'absence de syntaxes SQLite-only non abstraites dans `Core/Api/`, et (3) exécute les migrations + seed sur MySQL si un serveur est joignable (ou rapporte proprement le statut de validation dialectale hors-ligne). | Ne modifie jamais la base SQLite de production/test lors d'un check MySQL. |

## 3. Scénarios de Recette Utilisateur (UAT)
- **Persona 1 (Secrétaire / Président — Création d'adhérents & Stats réelles) :** Le Président crée/modifie des adhérents sur `/members` avec des genres distincts (`M`, `F`, `O` et `Non renseigné`), puis consulte `/stats` et `GET /api/v1/stats/kpis`. Les pourcentages affichés correspondent exactement aux données réelles en base (et non plus 54 % / 46 %), la part « Non renseigné » est visible, et la mention « Répartition estimée » a disparu.
- **Persona 2 (Visiteur / Famille RGPD — Inscription sans genre obligatoire + Garde API 422) :** Un visiteur s'inscrit sur `/register` sans renseigner le genre (l'inscription réussit normalement avec `gender = NULL`) puis un second visiteur renseigne `F` (persisté correctement). Une tentative d'injection d'une valeur invalide (`gender: "INVALID"`) sur l'API est rejetée en code `422`.
