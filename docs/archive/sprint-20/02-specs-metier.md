# Spécifications Fonctionnelles : Lot 4 — Sprint 20 (Transport SMTP Réel & Fiabilité Messagerie)

## 1. Règles de Gestion (RG) et Cas Limites
| ID RG | ID US Liée | Description de la règle métier | Comportement en cas d'erreur / Cas limite |
|---|---|---|---|
| `RG-01` | `US-LOT4-01` | Le CMS utilise un client SMTP natif PHP supportant `STARTTLS` (`tls`), `SSL/TLS` (`ssl`) et non chiffré (`none`), l'authentification `AUTH LOGIN` / `AUTH PLAIN` lorsque `smtp_username` est renseigné, ainsi qu'un délai d'expiration réseau borné (`smtp_timeout`, 2 à 30 secondes, défaut 10 s). | En cas de port invalide (< 1 ou > 65535), de timeout hors bornes ou de protocole inconnu, l'API rejette la sauvegarde avec un code JSend `422` et un toast d'erreur explicite. |
| `RG-02` | `US-LOT4-01` | Tous les envois transactionnels (e-mail de test `/sys-smtp`, mot de passe oublié, code 2FA e-mail, invitation OTP, renvoi OTP) passent par le service de messagerie centralisé avec en-têtes MIME UTF-8 (`From`, `To`, `Subject`, `Date`, `Message-ID`, `Content-Type: text/html; charset=UTF-8`). | Si l'adresse destinataire est invalide, l'envoi est refusé (code `422`) sans créer d'entrée corrompue. Pour « Mot de passe oublié », le message de retour reste neutre (anti-énumération) même si le serveur SMTP échoue. |
| `RG-03` | `US-LOT4-02` | Le mot de passe SMTP n'est jamais stocké en clair en base de données : il est chiffré (`enc:v1:...` via OpenSSL AES-256-GCM) dans `sys_settings` ou lu prioritairement depuis la variable d'environnement `SMTP_PASSWORD` (`.env`). L'API `GET /api/v1/settings` masque systématiquement `smtp_password` et expose uniquement `smtp_password_configured` (`"1"`/`"0"`) et `smtp_password_source` (`"env"`/`"db"`/`"none"`). | Laisser le champ mot de passe vide lors de la sauvegarde du formulaire `/sys-smtp` conserve le mot de passe existant sans l'écraser. Une case/action explicite permet de supprimer le mot de passe stocké en base. Si `SMTP_PASSWORD` est défini dans `.env`, un badge indique que la valeur est pilotée par l'environnement. |
| `RG-04` | `US-LOT4-03` | Un mode de transport (`smtp_transport`) permet de choisir entre `log` (journalisation locale / stub sans trafic réseau) et `smtp` (envoi réseau réel). Lorsque `APP_ENV=testing` est actif et que `smtp_transport` vaut `log` (valeur par défaut des fixtures QA), aucun socket réseau n'est ouvert : l'e-mail est journalisé en `sent` avec une réponse `250 2.0.0 OK [LOG/STUB]`. En mode `smtp`, même sous `APP_ENV=testing`, seuls les hôtes locaux (`127.0.0.1`, `localhost`, `::1`) sont autorisés pour les tests d'intégration ; tout hôte externe est bloqué en sécurité afin d'empêcher tout envoi accidentel vers Internet pendant la QA. | Si un test configure `smtp_transport = 'smtp'` avec un hôte externe sous `APP_ENV=testing`, le transport bascule/refuse l'émission externe avec un message explicite (`550 Blocked external SMTP in testing environment`) tracé en `failed`. |
| `RG-05` | `US-LOT4-04` | Chaque tentative d'envoi est enregistrée dans `email_logs` avec `status` (`sent` ou `failed`), `smtp_response` (réponse serveur ou erreur technique), `body_html` (contenu permettant une relance fidèle), `retry_count` (défaut `0`) et `last_retry_at`. Si un e-mail de test échoue (connexion refusée, timeout, erreur AUTH), l'entrée est persistée en `failed` et l'API renvoie HTTP 200 avec JSend `status: "error"`, `code: 502` et le détail d'erreur. | Les erreurs réseau/socket ne provoquent jamais d'erreur fatale PHP 500 ni de réponse vide : elles sont capturées proprement, tracées dans `email_logs` et restituées via un toast d'erreur dans `/sys-smtp`. |
| `RG-06` | `US-LOT4-04` | Dans l'onglet « 3. Historique des Envois » de `/sys-smtp`, le Superadmin visualise un badge de statut (`Envoyé` / `Échec`), le compteur de relances si `retry_count > 0`, et un bouton « Relancer » sur chaque ligne en statut `failed`. Le clic déclenche la ré-expédition avec le même destinataire, sujet et `body_html`, incrémente `retry_count`, met à jour `status`, `smtp_response` et `last_retry_at`, puis rafraîchit le tableau. | Tenter de relancer un e-mail inexistant retourne `404` ; tenter de relancer un e-mail déjà `sent` retourne `409` ; tout accès non-Superadmin retourne `403` et est journalisé dans `sys_logs`. |

## 3. Scénarios de Recette Utilisateur (UAT)
- **Persona 1 (Superadmin — Configuration sécurisée & envoi nominal) :** Le Superadmin se connecte via l'URL furtive, accède à `/sys-smtp`, configure les paramètres du serveur mail (hôte, port, chiffrement, mode `log` ou `smtp`, timeout et mot de passe SMTP) puis clique sur Sauvegarder. Après rechargement de la page, le badge confirme que le mot de passe est configuré (chiffré) sans jamais l'afficher en clair dans le DOM ni dans les réponses API. Il envoie un e-mail de test vers une adresse valide, obtient un toast de confirmation et retrouve l'envoi en statut `Envoyé` dans l'onglet Historique.
- **Persona 2 (Superadmin — Diagnostic d'incident SMTP & relance après correction) :** Le Superadmin bascule le transport sur `smtp` en pointant vers un serveur local injoignable (`127.0.0.1`, port fermé) et lance un e-mail de test. L'interface n'affiche aucun crash : un toast d'erreur explicite apparaît et l'onglet Historique affiche la ligne avec un badge rouge `Échec`, le détail de l'erreur réseau et un bouton « Relancer ». Le Superadmin corrige ensuite la configuration (bascule vers un transport opérationnel / `log`), retourne dans l'onglet Historique, clique sur « Relancer » : la tentative réussit, le statut passe à `Envoyé` et le compteur de relances indique `1`.
